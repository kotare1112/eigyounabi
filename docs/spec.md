## 1. サービス概要

営業ナビは、企業に起きた変化（新工場建設、設備投資、採用拡大など）を検知し、"買う理由が生まれた瞬間" を営業担当者に届ける SaaS である。従来の「企業名や業種で検索して営業先を探す」営業スタイルから、「変化の兆しをもとに優先順位付けされた営業先リストが自動的に届く」営業スタイルへの転換を目的とする。

### 1.1 課題（Before）

- 営業担当者は自らテレアポリストや企業データベースを検索し、架電先を選定する必要がある。
- 「なぜ今その会社に営業すべきか」という根拠が薄く、架電の成功率が低い。
- 提案内容や切り出し文言を営業担当者自身が都度考える必要があり、準備コストが高い。

### 1.2 提供価値（After）

- 営業担当者は毎朝、次の3点を受け取るだけでよい。
  1. 明日電話すべき5社（優先順位付きリスト）
  2. その企業が売れそうな理由（変化の兆しの根拠）
  3. 具体的な提案内容（切り出し文言・提案骨子）

## 2. ターゲットユーザー

| ユーザー種別 | 説明 |
|---|---|
| 主対象：営業担当者 | 日々の架電・提案準備を行う。毎朝のレポートを受け取り、実行するアクター。 |
| 主対象：営業マネージャー | チーム全体の商材登録・ターゲット設定・進捗管理を行う。 |
| 課金主体：企業（法人契約） | 月額 29,800円のサブスクリプションを契約する法人。 |

## 3. 全体フロー（コア機能 4 ステップ）

```
① 自社商品を登録 → ② 企業の変化を検知 → ③ 営業先を優先順位化 → ④ 次の行動を提案
```

### STEP 1: 自社商品を登録

**目的**：マッチング精度を上げるため、自社の商品・顧客像・解決できる課題を事前に登録する。

**入力項目**

| 項目 | 型 | 必須 | 説明 |
|---|---|---|---|
| 商品名 | 文字列 | ○ | 登録する商品/サービス名 |
| 商品カテゴリ | 選択 | ○ | 製造機器／IT・SaaS／人材／物流／その他 等 |
| 想定顧客像（業種・規模） | 複数選択 + 自由記述 | ○ | 例：製造業、従業員50名以上 |
| 解決できる課題 | タグ + 自由記述 | ○ | 例：人手不足、設備老朽化、生産能力不足 |
| 参考導入実績・事例 | 自由記述（任意） | - | レコメンド理由生成の参考情報として活用 |
| 価格帯 | 数値/レンジ | 任意 | 提案文生成時の参考情報 |

**機能要件**

- 商品は複数登録可能（企業が複数商材を扱う場合に対応）。
- 商品ごとに「どんな企業の変化が起きたら刺さるか」を裏側でタグ変換し、STEP2 の検知条件と紐付ける（例：「設備老朽化解消」タグ → 「工場新設」「設備投資」イベントと関連付け）。
- 登録後、いつでも編集・削除・複数商品の優先度設定が可能。

---

### STEP 2: 企業の変化を検知

**目的**：外部データソースをもとに、企業に起きた「買う理由になり得る変化」を自動収集する。

**検知する変化の種類（例）**

| 変化カテゴリ | 具体例 | データソース例 |
|---|---|---|
| 設備投資 | 新工場建設、新設備導入、拠点新設 | プレスリリース、官報、地方紙、自治体の企業誘致発表 |
| 採用拡大 | 大量採用、新拠点の求人急増 | 求人媒体API、企業採用ページのクローリング |
| 資金調達・業績 | 資金調達、増収増益発表 | IR情報、決算短信、ニュースリリース配信サービス |
| 組織変化 | 新規事業部設立、代表者交代 | 企業サイト、ニュースリリース |
| その他イベント | 展示会出展、新製品発表 | 業界メディア、SNS |

**機能要件**

- 外部データソース（ニュースAPI、求人API、IR情報API、Web スクレイピング等）と連携し、企業ごとの変化イベントを定期取得する（日次バッチを想定）。
- 取得したイベントを自然言語処理により分類・タグ付けし、STEP1 で登録した「解決できる課題タグ」とマッチングする。
- 検知したイベントは企業単位でタイムライン形式に蓄積し、履歴として保持する。
- 誤検知・重複イベントを除去するための正規化処理を行う。

**非機能要件**

- データソースの利用規約・APIのレート制限に準拠すること。
- 個人情報を含む採用ページ等のスクレイピングは、法令（著作権法、個人情報保護法）および対象サイトの利用規約に抵触しない範囲で実施すること。

---

### STEP 3: 営業先を優先順位化

**目的**：検知した変化イベントと自社商品のマッチ度から、営業すべき優先順位を自動算出する。

**優先順位算出ロジック（例）**

| 要素 | 説明 | 重み付け例 |
| --- | --- | --- |
| イベント新鮮度 | 変化が検知されてからの経過日数（新しいほど高評価） | 30% |
| 商品マッチ度 | STEP1 のタグと変化イベントのタグの一致度 | 40% |
| 企業規模・属性 | 想定顧客像との一致度（従業員数、業種等） | 20% |
| 過去の商談履歴 | 既存の接点有無、過去の商談結果（あれば） | 10% |

**機能要件**

- 上記ロジックに基づき「営業すべき理由」付きのスコアを算出し、企業を降順で並べたリストを生成する。
- 「営業すべき理由」は検知イベントの内容を要約して自然文で提示する（例：「〇〇社は先月新工場を稼働開始したため、生産設備の増強需要が見込まれます」）。
- 営業担当者ごと・チームごとにターゲットの担当割り振り（重複架電の防止）ができる。
- 既に商談中・NG企業をリストから除外するフィルタ機能を持つ。

---

### STEP 4: 次の行動を提案

**目的**：優先順位化された営業先ごとに、具体的な提案内容と最初のアプローチ文言を自動生成する。

**出力内容**

| 項目 | 説明 |
|---|---|
| 提案内容（骨子） | 検知した変化と自社商品を結びつけた提案の要点 |
| 最初の一言（架電トークスクリプト） | 電話での切り出しに使える短い文言 |
| メール／DM文面（任意） | メールでの初回コンタクト用テンプレート文 |
| 想定される反論・想定回答 | （拡張機能）よくある断り文句への切り返し例 |

**機能要件**

- 生成文はテンプレート + 生成AI（LLM）を用いてパーソナライズし、企業名・変化内容・自社商品名を差し込む。
- 営業担当者が文面を編集・保存できる（生成結果をそのまま使うだけでなく修正可能）。
- 架電結果（アプローチ済み／商談化／NG等）を記録し、STEP3 のスコアリング精度向上のフィードバックデータとして蓄積する。

---

## 4. 日次配信機能（営業担当者が毎朝受け取るもの）

- **配信タイミング**：毎営業日の朝（例：8:00 JST、契約企業ごとに設定可能）
- **配信方法**：Web アプリのダッシュボード表示 + メール通知（任意で Slack/Teams 連携）
- **配信内容**：
  1. 明日電話すべき5社（優先順位リスト、担当者ごとに個別化）
  2. 各社の「売れそうな理由」
  3. 各社への具体的な提案内容・最初の一言

---

## 5. 画面構成（サイトマップ）

1. **ログイン／会員登録画面**
2. **オンボーディング画面**（初回のみ：商品登録ウィザード）
3. **ダッシュボード（ホーム）**：本日のおすすめ営業先リスト
4. **企業詳細画面**：検知イベントのタイムライン、提案内容、アクション記録フォーム
5. **商品管理画面**：STEP1 の登録・編集
6. **チーム管理画面**：担当割り振り、メンバー管理（マネージャー向け）
7. **レポート／実績画面**：架電結果、商談化率などのKPI可視化
8. **設定画面**：通知設定、外部連携設定（Slack等）、料金プラン・請求管理

## 6. データモデル（概要）

```
Company（企業）
 ├─ id, 企業名, 業種, 従業員数, 所在地, 資本金 等の基本属性
 ├─ Events（検知イベント）[1:N]
 │    ├─ event_type（設備投資／採用拡大／資金調達 等）
 │    ├─ source（データソース）
 │    ├─ detected_at（検知日時）
 │    └─ summary（要約テキスト）
 └─ LeadScores（優先度スコア）[1:N]
      ├─ product_id（紐づく自社商品）
      ├─ score（算出スコア）
      ├─ reason（理由文）
      └─ calculated_at

Product（自社商品）
 ├─ id, 商品名, カテゴリ, 価格帯
 ├─ target_profile（想定顧客像）
 └─ solvable_issues（解決できる課題タグ）[N:N with Tag]

User（利用者）
 ├─ id, 氏名, メール, role（営業／マネージャー／管理者）
 └─ tenant_id（契約法人）

Action（営業アクション履歴）
 ├─ company_id, user_id, action_type（架電／メール／商談 等）
 ├─ result（成否・ステータス）
 └─ acted_at
```

## 7. 外部連携・データソース（想定）

| 連携先 | 用途 |
|---|---|
| ニュース・プレスリリース配信API | 設備投資・資金調達・組織変化の検知 |
| 求人媒体API／採用ページ | 採用拡大の検知 |
| 企業データベースAPI（帝国データバンク、東京商工リサーチ等） | 企業基本属性の取得・名寄せ |
| 生成AI API（Claude等） | 提案文・トークスクリプトの自動生成、イベント要約 |
| メール配信サービス | 日次レポートの配信 |
| Slack／Teams（任意） | チャット通知連携 |
| 決済・請求サービス（Stripe等） | 月額課金の管理 |

## 8. 料金プラン

| プラン | 月額 | 内容 |
|---|---|---|
| スタンダード | 29,800円／社（税別） | 商品登録数・ユーザー数に応じた基本機能一式 |

**訴求ロジック**：月額29,800円でも、100万円の契約が1件増えれば投資回収できる、という費用対効果を訴求する。

---

## 9. 非機能要件

| 分類 | 要件 |
|---|---|
| セキュリティ | 企業情報・個人情報を扱うため、通信のTLS化、アクセス権限管理（ロールベース）、データ暗号化を実施 |
| 可用性 | 日次バッチ処理の失敗時リトライ、配信遅延時のアラート機構 |
| 拡張性 | データソース追加・業種別テンプレート追加を容易にする設計（プラグイン的な検知ルール管理） |
| 法令対応 | 個人情報保護法、著作権法（スクレイピング範囲）、特定電子メール法（メール配信時）への準拠 |
| 監査 | 営業アクション履歴・スコア算出根拠のログを保持し、後から説明可能な状態を維持 |

## 10. 今後の検討事項（オープンイシュー）

- 検知対象とする外部データソースの優先順位・契約有無の確定
- スコアリングロジックの重み付けの初期値をどう決めるか（β版での実データ検証が必要）
- 生成AIによる提案文の品質保証・ハルシネーション対策（企業情報の誤記載防止）
- 無料トライアル／PoC期間の設計
- 既存SFA/CRM（Salesforce等）との連携要否
